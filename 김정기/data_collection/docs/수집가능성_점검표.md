# 수집 가능성 점검표 — 토스증권 커뮤니티

작성: 김정기 / 확인일 2026-10-19 (KST) / 소셜미디어 분석 6조
대상: 토스증권 WTS(`www.tossinvest.com`) 종목 커뮤니티(종목게시판)

> **결론 요약: 약관상 "명시적 금지"는 없지만 "명시적 허용"도 없다. 판단이 불명확하므로 수집기 구현(2단계)을 보류하고 보고한다.**
> 기술적으로는 과거 글 일괄 수집이 가능해 보이지만, 그 경로는 공개 API가 아니라 WTS 내부 API다.
> 토스증권에 연구 목적 이용 허락을 받으면 진행하고, 받지 못하면 대안 경로를 팀이 결정해야 한다(6절).

점검 방법: 약관·이용규칙·robots.txt는 원문을 직접 열람했다. 커뮤니티 동작은 브라우저로 종목 커뮤니티 화면을
**일반 사용자처럼 한 번 열고**, 화면이 이미 받아 둔 데이터의 구조만 확인했다.
점검 목적의 반복 요청, 스크립트 호출, 과거 글 페이지 넘기기는 하지 않았다.

### 1.4 robots.txt

원문: <https://www.tossinvest.com/robots.txt> (2026-10-19 확인)

```
User-agent: *
Allow: /
Disallow: /_ul/

User-agent: Googlebot
Allow: /

User-agent: bingbot
Allow: /
Disallow: /api/
```

- `www.tossinvest.com` 화면 경로는 모든 봇에 허용(`/_ul/` 제외). 종목 커뮤니티 화면 `/stocks/<코드>/community` 는 허용 범위다.
- 실제 글 데이터는 별도 도메인 `wts-cert-api.tossinvest.com` 에서 온다. 이 도메인에는 robots.txt가 없다(HTTP 404).
- robots.txt는 검색엔진 색인 규칙이지 이용 허락이 아니다. 허용돼 있다고 해서 약관상 수집이 허용된다는 뜻은 아니다.

### 1.5 관련 법령 (참고, 법률 자문 아님)

- **저작권법 제93조 (데이터베이스제작자의 권리)**: DB의 "상당한 부분"을 복제하거나, 상당하지 않은 부분이라도 반복적·체계적으로 복제해 통상적 이용과 충돌하면 침해가 될 수 있다. 100~200종목의 글을 매일 체계적으로 모으는 것은 여기에 걸릴 소지가 있다.
- **부정경쟁방지법 제2조 제1호 카목 (데이터 부정사용)**: 접근 권한 없는 자가 부정한 수단으로 데이터를 취득·사용하는 행위. 비영리 연구라도 판단은 사안별이다.
- **개인정보 보호법**: 닉네임·프로필 ID는 다른 정보와 결합하면 개인 식별이 가능할 수 있다. 수집 단계에서 저장하지 않는 것으로 대응한다.
- 공개된 웹 데이터 크롤링에 대한 국내 판례(숙박 앱 간 크롤링 사건 등)는 형사·민사 판단이 엇갈린다. 학생 과제라는 이유로 면책되지 않는다.

## 3. 커뮤니티 화면이 글을 불러오는 방식 (관찰)

종목 커뮤니티 화면(`https://www.tossinvest.com/stocks/A005930/community`)을 비로그인 상태로 한 번 열어 확인했다.

| 항목 | 관찰 결과 |
| --- | --- |
| 로그인 필요 여부 | **불필요.** 비로그인 상태에서 글 목록·본문·공감 수가 보인다. 응답의 `accessLevel` 값이 `EXTERNAL_PUBLIC` |
| 글 목록 API | `GET https://wts-cert-api.tossinvest.com/api/v4/comments?subjectType=STOCK&subjectId=<ISIN>&commentSortType=RECENT\|POPULAR` (WTS 내부 API, 공개 문서 없음) |
| 종목 식별자 | 종목코드가 아니라 ISIN(`KR7005930003`). 응답의 `board.stockCode` 에 `A005930` 형식으로 함께 옴 |
| 페이지네이션 | 커서 방식. 응답에 `key`(마지막 글 ID), `hasNext`, `totalCount` 가 오고 다음 요청에 `key` 를 넘김. 한 페이지에 약 11건 |
| 정렬 | `RECENT`(최신순), `POPULAR`(인기순) |
| 댓글(대댓글) | 글 목록에는 최상위 글만 온다(`parentId` 전부 `null`). 댓글은 글마다 따로 불러온다(`statistic.replyCount` 로 개수만 표시) |
| 비로그인 쿠키 | `deviceId`, `XSRF-TOKEN`, `UTK` 등 게스트 식별 쿠키가 발급됨. 요청 빈도를 기기 단위로 추적할 수 있는 구조 |

### 3.1 응답 필드와 기획안 항목 대응

| 기획안 항목 | 응답 필드 | 비고 |
| --- | --- | --- |
| 종목코드 | `board.stockCode` (`A005930`) | `A` 를 떼면 6자리 코드 |
| 작성시각 | `createdAt` (`2026-10-19T20:29:42.326512699+09:00`) | **KST 오프셋 포함, 나노초 정밀도.** 일부 글은 초 단위(`...20:28:25+09:00`) |
| 본문 | `message.title` + `message.message` | 제목이 빈 글도 많음. 목록 응답의 본문이 잘리는지는 미확인 |
| 글/댓글 구분 | `parentId` | 최상위 글은 `null` |
| 매수·매도 인증 | `execution.orderSide` (`BUY`/`SELL`), `execution.executedAt` | **체결 인증이 붙은 글에만 존재.** 수량·금액(`quantity`, `amountKrw`)도 같이 오지만 저장하지 않아야 함 |
| 보유(주주) 표시 | `holding.shareHoldingStatus` (`HOLDING`/`null`) | 화면의 "주주" 표시. 보조 지표로 쓸 수 있음 |
| 공감 수 | `statistic.likeCount` | `replyCount`, `readCount` 도 있음 |
| (작성자 뱃지) | `author.badge.title` ("1억대 자산가", "팔로워 부자" 등) | 기획안의 "인증 뱃지"가 아님. 작성자 자산 규모 표식이라 개인정보 성격이 강함. 저장하지 않는 것을 권장 |

**반드시 버려야 할 필드:** `author.*`(닉네임, `userProfileId`, 프로필 사진 URL, 자기소개, 팔로워 수), `authorUserProfileId`,
`execution.quantity / amountKrw / averageExecutionPrice*`, 이미지 URL.

## 4. 확인 항목별 결과

| 확인 항목 | 결과 | 확신도 |
| --- | --- | --- |
| 과거 글을 어디까지 볼 수 있는가 | 삼성전자 `totalCount` = **2,084,832건.** 커뮤니티 시작(2021-05-20) 이후 전체가 커서로 이어져 있을 가능성이 높음 | **추정.** 실제로 과거 페이지를 넘겨 보는 검증은 하지 않음(대량 요청이 되므로 허락 전에는 하지 않음) |
| 인증 뱃지 노출 | 체결 인증(`execution.orderSide` BUY/SELL)이 글 단위로 노출됨. 주주 여부(`holding`)도 노출 | 확인 |
| 작성시각 정밀도 | 초~나노초, `+09:00` 포함 | 확인 |
| 요청 빈도 제한 | 공개된 한도 없음. 게스트 쿠키로 기기 단위 추적 가능. 과도한 요청 시 차단 가능성 있음 | 미확인 |

### 4.1 요청량 추정 (허락을 받는 경우를 위한 참고)

- 삼성전자 최신순 첫 페이지 11건이 저녁 시간 약 6분 분량이었다. 대형주는 하루 수천 건 이상으로 보인다.
- 최상위 글만 모아도 "하루 글 수 ÷ 11" 번의 요청이 종목마다 필요하다. 댓글까지 모으면 글마다 요청이 추가된다.
- 150종목 × 하루 평균 300건 가정, 글만 수집 → 하루 약 4,100회. 2초 간격이면 약 2.3시간.
- 댓글까지 수집하면 요청이 수 배로 늘어난다. 과거 일괄 수집(예: 6개월)은 하루 수집량의 약 180배다.

## 5. 결론: "과거 일괄 수집" vs "매일 누적 수집"

| 관점 | 판단 |
| --- | --- |
| 기술적 가능성 | 비로그인으로 열람 가능하고 커서가 과거로 이어지므로 **과거 일괄 수집이 기술적으로는 가능해 보인다** |
| 약관·규칙상 허용 | **불명확.** 커뮤니티 약관에 크롤링 금지 조항은 없다. 그러나 ① 글을 가져가는 공식 API가 없고, ② 온라인 서비스 이용약관 제10조가 "토스앱·WTS가 아닌 매체를 통한 접근"을 이용 제한 사유로 두고 있으며, ③ 체계적 대량 복제는 DB제작자 권리·데이터 부정사용 쟁점이 생길 수 있다 |
| 판정 | 작업 지시의 중단 조건("약관상 금지이거나 불명확하면 멈추고 보고")에 해당. **2단계 구현을 보류한다** |

허락을 받는다면 **과거 일괄 수집**이 분석상 유리하다(백분위 창 60일 확보, 사건 전후 비교 가능).
허락 범위가 좁다면 **허락받은 시점부터 매일 누적 수집**하고, 기획안 3절대로 60거래일 × 종목 패널로 간다.
어느 쪽이든 "허락 → 방식 결정" 순서이고, 방식이 허락 여부를 앞서지 않는다.

   - (c) 주제 범위 축소: 소수 종목 × 짧은 기간 수동 표본으로 방법론 비교 중심 보고
