# 개발 기록 — 토스증권 감성 분석 파이프라인

작성일: 2026-10-11 / 작성: 조현호
대상 저장소 경로: `조현호/toss_sentiment/`

기획안에 적은 분석 설계를 실행 가능한 코드로 옮긴 작업의 기록이다.
무엇을 만들었고, 왜 그렇게 결정했고, 어디까지 확인했는지를 남긴다.

---

## 1. 작업 배경

중간보고서 원고에는 연구 질문, 변수 정의, 수집·전처리 절차, 감성 검수와 시차 분석 설계가
정리되어 있었지만 실행 코드가 없었다. 기존 코드는 `tmp/` 아래에 PDF를 만드는 일회성
스크립트 네 개가 흩어져 있었고, 분석 절차는 문서로만 존재했다.

이 상태에서는 두 가지 문제가 있었다.

- 설계와 구현이 분리되어, 실제로 돌려 보기 전까지 절차의 빈틈을 발견할 수 없다.
- 팀원별로 다른 방식으로 분석하면 결과를 합치거나 재현할 수 없다.

그래서 **설계 문서의 각 절차를 그대로 하나의 단계(stage)로 만들고,
단계 전체를 하나의 진입점에서 실행하는 컨트롤러**를 만들었다.

## 2. 만든 것

### 2.1 구조

```
조현호/toss_sentiment/
├── run_pipeline.py            컨트롤러 진입점 (CLI)
├── config/pipeline.yaml       종목·기간·임계값 등 모든 설정
├── requirements.txt
├── README.md                  사용법
├── docs/개발기록.md            이 문서
└── pipeline/
    ├── config.py              설정 로딩과 검증
    ├── context.py             로깅, 산출물 입출력, 실행 기록
    ├── registry.py            단계 정의·선택·실행
    ├── lexicon.py             주식 은어 감성 사전
    └── stages/                8개 단계 모듈
```

### 2.2 단계 구성

| 순서 | 단계 | 하는 일 | 원고 대응 |
| --- | --- | --- | --- |
| 1 | `collect` | 커뮤니티 텍스트 확보 | 02장 데이터 수집 설계 |
| 2 | `clean` | 중복·홍보 제거, 시간 기준 정리 | 02장 정제 및 시간 기준 |
| 3 | `sentiment` | 감성 분류와 성능 검수 | 03장 조작적 정의·분류 계획 |
| 4 | `market` | 수정주가·거래량·시장지수 확보 | 02장 가격 자료 |
| 5 | `aggregate` | 거래일 정렬과 감성 지수 산출 | 02장 시간 기준, 03장 지표 |
| 6 | `merge` | 분석용 패널 구성 | 02장 거래일 단위 구조 |
| 7 | `analyze` | 기술통계·시차상관·회귀·Granger | 03장 분석 절차 ①~④ |
| 8 | `report` | 결과 요약 작성 | 04장 기대 산출물 |

### 2.3 컨트롤러 기능

```bash
python run_pipeline.py plan                  실행 계획만 확인
python run_pipeline.py run                   전체 실행
python run_pipeline.py run --from analyze    특정 단계부터
python run_pipeline.py run --only sentiment  특정 단계만
python run_pipeline.py run --until merge     특정 단계까지
python run_pipeline.py run --force           캐시 무시하고 재실행
python run_pipeline.py status                단계별 산출물 상태
```

- **산출물 캐싱**: 산출물이 입력보다 새것이면 그 단계를 건너뛴다.
  감성 사전만 고치면 `--from sentiment` 로 뒤쪽만 다시 돌리면 된다.
- **실행 기록**: 실행마다 `runs/<실행ID>/manifest.json` 에 설정 지문(해시),
  단계별 소요 시간, 행 수, 주요 지표를 남긴다. 보고서의 어떤 수치가
  어떤 설정·어떤 실행에서 나왔는지 추적할 수 있다.
- **한계 기록 누적**: 각 단계가 발견한 한계·확인 사항을 `runs/notes.json` 에
  단계별로 모으고, 결과 요약 6절에 자동으로 옮긴다.
  `report` 단계만 따로 실행해도 앞 단계들이 남긴 기록이 유지된다.

## 3. 설계 결정과 이유

### 3.1 수집기를 저장소에 넣지 않았다

토스증권 웹사이트에 커뮤니티 화면이 있다는 사실이 과거 전체 자료의 수집 가능성이나
수집 허용을 뜻하지 않는다. 이용약관·robots 규칙·접근 범위를 확인하기 전에
자동 수집 코드를 저장소에 넣으면, 확인 절차를 건너뛰고 실행될 위험이 있다.

그래서 수집을 **어댑터**로 분리했다.

- `manual_csv` — 팀이 허용된 범위에서 확보한 CSV를 읽는다. 실제 분석용 경로다.
- `sample` — 합성 표본으로 전체 절차를 점검한다. 실데이터가 아니다.

그리고 `collect.collection_approved` 플래그를 두어 기본값을 `false` 로 했다.
이 값이 `false` 인 채로 수집본을 읽으면 "이용 조건 확인 결과를 점검표에 남겨야 한다"는
기록이 결과 요약에 남는다.

확인이 끝나면 허용 범위의 수집기를 만들어 `manual_csv` 입력 형식(`stock_id`,
`post_id`, `parent_id`, `text`, `created_at`)으로 저장하면 된다.

### 3.2 합성 표본에 관계를 심어 두었다

실데이터가 없는 상태에서 "분석 코드가 맞게 동작하는가"를 확인할 방법이 필요했다.

`sample` 어댑터는 종목별로 서서히 변하는 심리 흐름을 만들고,
`market` 의 `sample` 경로가 **전일 심리를 다음 거래일 수익률에 약하게 반영**한다.
분석 단계가 `k=+1`(감성 선행)에서 이 관계를 탐지하면 파이프라인이 제대로 도는 것이다.

이 수치는 연구 결과가 아니다. `report` 단계가 요약 맨 위에 경고 문구를 자동으로 붙인다.

### 3.3 거래일 정렬을 코드로 고정했다

원고의 시간 기준을 그대로 구현했다.

- 집계 구간은 **직전 거래일 종가 이후 ~ 당일 종가**.
- 종가 시각(기본 15:30) 이후에 쓴 글은 다음 거래일 구간으로 넘어간다.
- 비거래일 글도 같은 규칙으로 다음 거래일에 배정된다.
- 당일 종가 이후의 글로 당일 수익률을 설명하는 일이 구조적으로 생기지 않는다.

거래일 달력은 시장 자료에서 가져온다. 그래서 `market` 단계를 `aggregate` 앞에 두었다.

### 3.4 결측과 0을 구분했다

글이 없는 날의 감성 지수를 0으로 두면 "중립"이라는 잘못된 신호가 된다.
글 수가 `aggregate.min_posts`(기본 5) 미만인 날은 감성을 **결측**으로 두고
글 수는 0으로 기록한다. 그리고 최소 글 수 기준을 1·5·10으로 바꾼
민감도 분석을 `analyze` 단계가 항상 함께 산출한다.

### 3.5 다중검정을 보정했다

시차 k를 -5부터 +5까지 11번 탐색하면 우연히 유의한 결과가 나오기 쉽다.
Benjamini-Hochberg 보정값을 함께 계산하고, 보정 후 유의 여부를 별도 컬럼으로 보고한다.

### 3.6 시계열 의존성을 고려했다

일별 수익률·감성은 자기상관이 있어 일반 표준오차를 쓰면 유의성이 과장된다.
회귀는 Newey-West HAC 표준오차(기본 maxlags=5)를 사용한다.

Granger 검정은 보조로만 둔다. ADF로 정상성을 먼저 확인하고,
충족되지 않으면 "보조 참고"라는 기록을 남긴다.

### 3.7 개인정보를 분석 데이터에 남기지 않았다

`clean` 단계가 `author`, `nickname`, `profile_url`, `user_id` 컬럼을 제거한다.
수집본에 섞여 들어와도 분석용 테이블에는 남지 않는다.
`.gitignore` 로 `data/`, `runs/`, `output/` 전체를 저장소에서 제외했다.
원문 저장·재배포가 제한될 수 있으므로 코드와 집계 결과만 공유한다.

## 4. 개발 중 발견하고 고친 문제

설계 문서만으로는 보이지 않던 문제들이다. 실제로 돌려 보면서 찾았다.

### 4.1 홍보성 글 판정이 정상 표현까지 제거했다

처음에는 "같은 문구가 분석 기간 전체에서 4회 이상 반복되면 홍보"로 판정했다.
실행해 보니 13,010건 중 12,965건이 제거되어 45건만 남았다.

주식 커뮤니티에서 "손절했다", "반등 간다" 같은 표현은 6개월 동안 수백 번 반복되는
정상적인 발화다. 기간 전체를 기준으로 삼으면 이런 상용 표현이 전부 홍보로 분류된다.

**판정 범위를 같은 종목·같은 날 안으로 좁혔다.** 하루에 같은 문구가 4회 이상
반복되면 홍보로 보고 첫 건만 남긴다. 수정 후 제외율이 정상 범위로 돌아왔다.

이 문제는 실데이터에서도 그대로 발생했을 것이고, 발견하지 못했다면
표본의 대부분을 잃은 채로 분석을 진행했을 것이다.

### 4.2 설정 경로가 두 번 결합됐다

`sentiment.gold_path: data/labels/gold.csv` 설정값을 다시 data 디렉터리 기준으로
결합해서 `data/data/labels/gold.csv` 를 찾고 있었다. 파일이 없으니 성능 평가가
조용히 건너뛰어졌다. 오류도 나지 않아서 더 위험했다.

설정의 상대 경로를 **프로젝트 루트 기준**으로 해석하는 `Config.resolve()` 를 만들고,
`collect.manual_csv.input_dir`, `market.input_dir`, `sentiment.gold_path`
세 곳을 모두 바꿨다.

### 4.3 보고서 단계만 실행하면 한계 기록이 비었다

한계·확인 사항을 메모리에만 들고 있어서, `--only report` 로 요약만 다시 만들면
앞 단계들이 남긴 기록이 사라졌다.

기록을 `runs/notes.json` 에 **단계별로** 영속화하고, 단계를 다시 실행할 때
그 단계의 기록만 지우도록 했다. 이제 어떤 순서로 실행해도 기록이 정확하다.

### 4.4 종목 코드의 앞자리 0이 사라졌다

결과 요약에서 `000660` 이 `660` 으로, `005930` 이 `5930` 으로 나왔다.
CSV를 읽을 때 종목 코드가 숫자로 해석된 탓이다. 보고서 표를 만드는 단계에서
종목 코드를 문자열로 읽도록 고쳤다.

### 4.5 statsmodels 버전에 따라 ADF 반환 형식이 달랐다

`adfuller` 가 버전에 따라 튜플 또는 결과 객체를 돌려주고, 경고도 출력됐다.
두 형식을 모두 처리하는 `_adf_pvalue()` 헬퍼로 감쌌다.

## 5. 검증 결과

### 5.1 합성 표본 전체 실행

8단계 전부 실행되고 산출물이 생성되는 것을 확인했다.

```
collect   13,127건 (3종목 × 약 183일)
clean     13,127건 (제외 0건)
sentiment 사전 기반 분류 완료
market    393행 (3종목 × 131거래일)
aggregate 393행, 감성 결측률 0
merge     393행 패널
analyze   기술통계·시차상관 33행·회귀 39행·Granger 36행
report    결과 요약 생성
```

### 5.2 심어 둔 선행 관계를 탐지했다

합성 데이터에 "감성이 다음 거래일 수익률을 약하게 앞선다"는 관계를 심어 두었고,
분석 단계가 이를 찾아냈다.

| 검증 항목 | 결과 |
| --- | --- |
| 최대 시차 상관 | `k=+1`(감성 선행)에서 최대 — 삼성전자 0.317, 카카오 0.474 |
| H2 회귀 (감성 → 다음 거래일 수익률) | 3종목 모두 유의, 계수 0.011~0.022 |
| Granger 감성 → 수익률 | p = 0.0002 |
| Granger 수익률 → 감성 | p = 0.21 (유의하지 않음) |

방향이 **구분되어** 나온 것이 핵심이다. 선행과 후행을 섞어 보고하지 않는다는
연구 질문의 요건을 코드가 만족한다는 뜻이다.

동시에 ADF 검정이 감성 지수의 정상성 미충족(p=0.56)을 잡아내고
"Granger 결과를 보조 참고로만 본다"는 기록을 남겼다. 경고 장치도 동작한다.

### 5.3 실데이터 경로 검증

합성 데이터가 아닌 실제 입력 형식으로도 전체 경로를 확인했다.

- 커뮤니티 CSV를 `data/raw/posts/` 에 종목별로 두고 `collect.source: manual_csv` 로 실행 → 정상
- 시세 CSV(`<종목코드>.csv`)와 지수(`index.csv`)를 두고 `market.source: csv` 로 실행 → 정상
  시장 수익률이 패널에 결합되는 것까지 확인(결측 3건 = 종목별 첫 거래일, 정상)
- 평가 표본 300건을 `data/labels/gold.csv` 에 두고 실행 →
  클래스별 정밀도·재현율, macro-F1 0.91, 혼동행렬 산출 확인

### 5.4 그림 산출

시차별 감성-수익률 상관 그래프가 한글 폰트로 정상 렌더링되는 것을 확인했다
(`output/figures/07_시차상관.png`).

## 6. 현재 상태

### 완료

- 파이프라인 컨트롤러와 8개 단계 전부 동작
- 합성 표본 / 실데이터 입력 형식 양쪽 경로 검증
- 사전 기반 감성 분류 기준선과 성능 평가 절차
- 시차 상관(BH 보정), HAC 회귀, Granger, 민감도 분석
- 실행 기록과 한계 기록 자동 수집
- 사용법 문서(README)와 이 개발 기록

### 미완료 — 실데이터가 필요한 부분

- 수집 가능 여부 확인 (이용약관·접근 범위·시각 정밀도) 및 점검표 작성
- 분석 종목과 기간 확정 (현재 설정은 제안값)
- 실제 커뮤니티 자료 수집
- 예비 텍스트 300건 2인 독립 라벨링 및 불일치 조정
- 한국어 감성 모델과 사전 기준선 비교 (`sentiment.method: model` 경로는 구현되어 있으나 미실행)
- 실증 분석 결과 산출 및 해석

### 기획안 대비 미구현

제안 덱의 다음 항목은 아직 코드로 옮기지 않았다.

- 5개 하위 지표(스탠스·관심도·쏠림·키워드·인증)와 백분위 변환, 섹터·시장 계층 집계
- MoA(Mixture-of-Agents) 분류와 단일 LLM·사전 기준선 비교
- H4(극단 지수 이후 역행) 이벤트 분석
- 대시보드 화면

현재 구현은 **단일 감성 지수 S 기준의 H1·H2·H3 검증**까지다.
나머지는 실데이터 확보 이후 같은 컨트롤러에 단계를 추가하는 방식으로 확장할 수 있다.

## 7. 팀원이 바로 할 수 있는 일

```bash
cd 조현호/toss_sentiment
pip install -r requirements.txt
python run_pipeline.py run     # 합성 표본으로 전체 절차 확인
open output/보고서_결과요약.md
```

실제 자료를 확보했다면 `config/pipeline.yaml` 에서
`collect.source` 를 `manual_csv`, `market.source` 를 `csv` 로 바꾸고
README의 "데이터 넣는 방법"을 따른다.

분석 조건을 바꿔 보고 싶다면 코드가 아니라 `config/pipeline.yaml` 만 고치면 된다.
최소 글 수, 시차 범위, 종가 시각, HAC lag, 민감도 후보 전부 설정값이다.
